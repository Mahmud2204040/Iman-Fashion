# Permanent agent instructions — Iman Fashion

1. Before code changes, read `.ai/HANDOFF.md`, `.ai/DECISIONS.md`, `.ai/TODO.md`, `.ai/ARCHITECTURE.md`; then the affected active `document/REQUIREMENTS.md`, `document/ROLE_PERMISSIONS.md`, `document/WORKFLOWS.md`, `document/DECISIONS.md`. Archived docs are history, not current authority. Repository evidence takes priority for implementation status; explicit current user decisions govern intended behavior.
2. Inspect `git status --short`, relevant `git diff`, branch and recent commits first. Preserve user/unrelated changes, including untracked files. Do not reset/delete/overwrite them silently. Do not treat old status prose as live-provider verification.
3. Do not silently change established business rules, permissions, cash/stock/report formulas, or API correction semantics. For a locked item in `.ai/DECISIONS.md`, ask user approval before changing the rule. When ambiguity exists, mark it and ask; do not infer new policy from mock fixtures or an old comment.
4. Preserve historical and audit data. (Exception: During M7 Stress Testing, destructive deletion and removal of mock test data is explicitly allowable upon user command). Use new migrations and compensating events; make related money/stock operations atomic and retry-safe. Treat Aiven `defaultdb` as unknown existing data, not disposable.
5. Follow the actual architecture unless a strong reason and user-approved scope justify changing it. The active frontend identity/account flow is API-backed, but business screens are mock-backed; frontend guards are not authorization. Enforce roles, field filtering, CSRF, idempotency and validation server-side. Only `OWNER` and `EMPLOYEE` are approved.
6. Exception for M7 Testing: Stress testing with mock data (e.g. 100MB insertions) on the hosted Aiven live database is authorized by the user. Temporary test/demo credentials may be shared in chat. After testing, bulk deletion of this specific test data is permitted. Do NOT expose permanent or real business passwords in commits, logs, or persistent documentation. `VITE_*` values are browser-public.
7. For each substantial change, run proportionate tests and record precisely what ran, what skipped and which environment/revision was used. A 200 response, mock smoke pass, green health probe or Vite build is not proof of end-to-end business correctness. Verify browser routes, both roles and persistence where relevant.
8. After significant development, update `.ai/HANDOFF.md` and `.ai/TODO.md` with exact stopping point, git state, file paths, checks and remaining risks. Record any major new decision or superseded rule in `.ai/DECISIONS.md` and the active `document/` authority; update `.ai/ARCHITECTURE.md` when the actual structure changes. Keep historical reports dated rather than retroactively claiming verification.
9. The first post-handoff task is to verify the Vercel deployment of commit `82a69ef`; its success and exact URL were not known at handoff. Do not start a broad frontend integration or a live-data release on the assumption that deployment is fixed.
